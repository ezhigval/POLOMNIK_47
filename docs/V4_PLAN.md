## Этап 12 — автодеплой с `main` и аккуратные миграции

После этапа 1, **параллельно** с продуктом 9–11 (не блокирует ленту). Сейчас деплой вручную: `make deploy` с машины агента/владельца. Цель: **мерж в `main` после зелёного CI = выкладка на https://tikhvin-palomnik.ru**, без второго ручного шага.

### Автодеплой

- Триггер: успешный CI на `main` (не на feature-ветках, не на PR).
- Один деплой за раз: `concurrency` в GitHub Actions, очередь, не два `docker compose build` на ВМ одновременно.
- Тот же путь, что сейчас: `deploy/yandex/deploy.sh` / `make deploy`. Каталог `/opt/polomnik`. **Не** `compose down -v`.
- **Не** rsync `.env.production` с раннера на ВМ (секреты живут только на сервере). Уже в `deploy.sh`.
- После `up`: `https://api.tikhvin-palomnik.ru/health/ready` = 200. При падении health — не считать релиз успешным.
- Откат: checkout известного тега → тот же пайплайн. Миграции только аддитивные, поэтому «назад» по данным не через `goose down` на проде.
- Секреты раннера — GitHub Actions Secrets (имена в [V4_OWNER_SETUP.md](V4_OWNER_SETUP.md)), не в репозитории. SSH-ключ деплоя ≠ токен Cloudflare и ≠ `ADMIN_TOKEN`.

### Миграции (goose) без потери данных

- На проде только **`goose up`**. Не `down`, не `reset`, не ручной `DROP`.
- Новый файл = следующий свободный номер. **Не править уже применённые** `000NN_*.sql` на проде.
- Данные с `;` внутри строк (новости, HTML) — только в `-- +goose StatementBegin` / `StatementEnd` (урок 00025).
- `UPDATE` существующих рядов — отдельная новая миграция (как 00026 «духовник»→«священник»), не переписывание старого INSERT.
- Postgres named volume не трогать. Сид на проде не затирает живые туры/новости/заявки (compose seed идемпотентный / no-op на заполненной БД — не включать destructive seed).
- После миграций, которые меняют публичные туры/новости: сбросить Redis `tours:namespace` / `news:namespace`, иначе главная до 5 минут отдаёт старое.

Пока этап 12 не в коде: выкладка по просьбе владельца, `make deploy`. Два параллельных деплоя не запускать.

**В коде (этап 12):** workflow `.github/workflows/deploy.yml` — после зелёного CI на push в `main`, `concurrency: production-deploy`, тот же `deploy/yandex/deploy.sh` с `DEPLOY_CI=1` (не требует локальный `.env.production`), проверка `https://api.tikhvin-palomnik.ru/health/ready`. Секреты: `DEPLOY_SSH_KEY` (обяз.), опционально `DEPLOY_REMOTE`, `DEPLOY_DIR`. Без ключа workflow падает с понятным сообщением — ручной `make deploy` по-прежнему работает.

## Этап 13 — флаги тура в админке (корректировка)

После этапа 1, **параллельно** с 9–12. Поля уже есть (`is_active`, `is_regular`, `is_hot`, `overbooking_enabled`). Владелец зафиксировал смысл. Не выдумывать цены.

Тур **регулярный**, если он существует как факт предложения, но **конкретный выезд не запланирован**. Тогда на витрине и в карточке **нет цены и нет дат** (поля в админке при галочке скрывать, на сайте не показывать «0 ₽» и пустой календарь). Заявку принимать тем же потоком; сумму не назначать, пока владелец не скажет иначе (сейчас `total_price=0`).

Четыре независимые галочки (можно сочетать, кроме скрытого неактивного):

| Админка | Поле | На сайте |
|---------|------|----------|
| **Активный** | `is_active` | Виден в каталоге и по прямой ссылке. Снят — скрыт с витрины. |
| **Регулярный** | `is_regular` | Без даты и без цены. Не путать с «скрыт»: регулярный + активный = виден. |
| **Популярный** | `is_hot` | Подсветка карточки и **тег «Популярный»** (не «Hot» / не обязательно «Хит сезона»). |
| **Овербукинг** | `overbooking_enabled` | Когда места кончились (`slots_left=0`), заявку **всё равно** можно оставить; бронь помечается `overbooked`. Не уводить карточку в «нельзя записаться», если галочка включена. |

Не смешивать с закреплением новостей. Не автопомечать Успение и листовки регулярными. Листовки без цен по-прежнему `is_active=false`, пока владелец не даст дату/цену **или** явно не включит «Регулярный» + «Активный».

Код этапа: подписи в админке на русском; тег популярности единообразно «Популярный»; регулярный — не рендерить блоки цены/дат на главной, `/search`, карточке, JSON-LD Offer/event с фиктивной датой.

## Этап 14 — горящий тур и скрытие прошедших

После этапа 13. Не путать с `is_hot` («Популярный»).

| Условие | Поведение |
|---------|-----------|
| **Выезд сегодня** (`date_start` = сегодня, UTC) | На витрине `is_burning=true`, тег **«Горящий тур»**, скидка от базовой цены если задан `HOT_TOUR_DISCOUNT_PERCENT` |
| **Дата окончания прошла** (`date_end` < сегодня) | Worker раз в час ставит `is_active=false`, Telegram менеджерам «Тур скрыт» (outbox) |
| **Регулярный тур** (`is_regular`) | Горящий/скрытие по дате **не** применяются |

Скидка **не выдумывается**: env `HOT_TOUR_DISCOUNT_PERCENT` (0 по умолчанию = только тег без скидки). Владелец задаёт процент на проде; открытый вопрос — подтвердить величину.

Логика: `domain.TourCatalogContext`, `TourLifecycleService`, worker `cmd/worker`. Бронь считает сумму с учётом скидки в день выезда.

## Definition of Done

- Решение владельца, не догадка
- Логика в domain/application, канал — адаптер
- Секреты в env, несекретное — «Настройки», если ключ уже в модели
- Тесты `go test` / `go vet` / `npm run lint` / `npm run build`
- Прод — только по просьбе **пока нет этапа 12**; после него мерж в `main` = деплой. Postgres не сбрасывать
- Этап 1 не подменяет этапы 7–8 и не подменяет продукт 9–11
- Этап 12 не подменяет 9–11; не включает live Bitrix/оплату
- Этап 13: не выдумывать цену регулярного тура; не автопомечать чужие туры регулярными
- Этапы 9–11: доменные правила не в Fiber и не во frontend; код ленты не начинать до 1 и 9–10
