# Project Decisions

Дата фиксации: 2026-05-20.

## 1. Технологические решения

- Backend пишется на Go.
- HTTP framework для backend: Fiber.
- Go module: `palomnik`.
- Frontend: Next.js, TypeScript, TailwindCSS.
- База данных MVP: PostgreSQL.
- Migration tool: goose-compatible SQL migrations.
- Cache MVP: Redis, если он нужен для производительности и не усложняет первый запуск.
- Инфраструктура: Docker, Docker Compose, Nginx, VPS.

## 2. Структура репозитория

Репозиторий делится на три верхнеуровневые зоны:

```text
docs/      - документация
backend/   - Go backend
frontend/  - Next.js frontend
```

Старый код в корне является заготовкой и должен быть заменен при создании backend skeleton.

## 3. Глобальная стратегия разработки

Этапы:

1. **Backend logic** — готово.
2. **Frontend logic + marketing UX** — готово (~95%).
3. **Контент и внутреннее тестирование** — текущий фокус.
4. **Подключение внешних сервисов** — финальный этап: Telegram, Bitrix24, 1C, аналитика.

**Правило:** весь код адаптеров пишется заранее; живые credentials и отладка — только после наполнения сайта и smoke-тестов.

Внешние сервисы подключаются через порты (`CRMPort`, `AccountingPort`, `NotificationPort`) без переписывания domain/application.

## 4. Архитектурное решение

Backend обязательно строится по принципам гексагональной архитектуры:

- domain не зависит от framework, базы, CRM, 1C, Redis и HTTP;
- application/use cases зависят от портов;
- adapters реализуют порты;
- Fiber, PostgreSQL, Redis, Bitrix24 и 1C находятся на внешнем слое;
- замена PostgreSQL-адаптера на Bitrix24/1C-адаптер не должна менять domain и use cases.

## 5. MVP 1

Первый MVP включает:

- backend API;
- собственную доменную модель;
- хранение данных через локальный database adapter;
- публичные API для туров, отзывов и заявок;
- management API для наполнения данных и обработки заявок;
- заготовки портов под Bitrix24 и 1C;
- fake/noop adapters для внешних интеграций;
- тесты бизнес-логики;
- Docker Compose для локального запуска.

Первый MVP не включает:

- активную интеграцию Bitrix24;
- активную интеграцию 1C;
- регистрацию пользователей;
- личный кабинет;
- online payments;
- полноценную систему ролей;
- мобильное приложение.

## 6. Bitrix24

Bitrix24 временно убран из первого MVP.

В первом MVP нужно:

- не писать business logic под конкретные поля Bitrix24;
- не угадывать `entityTypeId`, `STAGE_ID` и пользовательские поля;
- создать порты и noop/fake adapter;
- оставить документацию для будущей интеграции.

Bitrix24 возвращается на этапе интеграций.

## 7. 1C

1C добавляется на этапе интеграций.

До уточнения формата обмена нельзя придумывать:

- формат документов 1C;
- способ обмена;
- учетные статусы;
- правила синхронизации оплат;
- правила бухгалтерского учета.

В первом MVP можно только подготовить порт для будущего accounting/export adapter.

## 8. API MVP

В MVP делаем как можно больше backend API, но без привязки к Bitrix24 и 1C.

Разрешено в MVP:

- публичный read API;
- booking API;
- reviews API;
- management API для tours/bookings/reviews;
- техническая защита management API простым `X-Admin-Token`, если endpoint-ы будут доступны не только локально.

Не разрешено в MVP без отдельного решения:

- JWT auth;
- пользовательский login;
- online payment flow;
- Bitrix24-specific public contracts;
- 1C-specific public contracts.

## 9. Документация

Документация должна быть цельной и логичной. Файлы в `docs/` заменяют старые разрозненные документы.

Если агент находит неясность:

- он фиксирует вопрос;
- не придумывает бизнес-решение;
- не меняет scope самостоятельно.

## 11. Состояние v2.0 (2026-08-23)

Актуально. Сверка: GitHub `main` = прод, теги `v2.0.0` / `v2.0.1`. Подробности: [STATUS.md](STATUS.md).

- Публичный домен один: `tikhvin-palomnik.ru` (`api.` и `www` — A на ту же ВМ).

- Главная — блоки CMS; фабрики страниц в UI нет.
- Получатели уведомлений: блоки событий, получатель = **канал + адрес** (не только Telegram-username).
- Имя/телефон/почта сайта — в настройках админки (не секреты).
- Mailer / SEO / Метрика — код готов; включение по [V2_OWNER_SETUP.md](V2_OWNER_SETUP.md).
- Bitrix24 и 1С по-прежнему не live.
- Бэклог v2 закрыт freeze `v2.1.0`. Дальше: [V3_PLAN.md](V3_PLAN.md).

## 12. План v3 (2026-08-23)

Зафиксировано владельцем как состав линейки. Этапы 0–1 в `main` (2026-08-23); этап 2 в коде (меню по RBAC, фильтры заявок/CSV, шаблоны ролей как пресеты существующих прав); этап 3: identity `(user_id, provider, subject)` и слияние в текущего пользователя (заявки, избранное, треды, пассажиры). Конфликт имени/почты/телефона не перезаписывается молча. Правка профиля: `PATCH /me` (имя, почта, телефон; смена телефона при callcheck — как регистрация). Пассажиры: ФИО, телефон, ДР, паспорт; без СНИЛС; маска в мессенджерах. СНИЛС нет. Этапы 4–10 и v4 не начаты.

Шаблоны ролей (имена из плана; наборы — те же permission, что уже режут API/UI):

| Шаблон | Права |
|--------|--------|
| менеджер заявок | `manage_bookings`, `manage_support` |
| рекламщик | `view_stats` (Метрика, без выдуманных визитов) |
| сммщик | `manage_content` |
| директор | все, кроме `manage_roles` |
| разработчик | `manage_integrations`, `view_stats` |

- Сначала платформа (безопасность, кэш, бэкапы), затем продукт без ключей, затем адаптеры до состояния «вписать секрет».
- Оплата Сбер и/или ЮKassa — позже, один `PaymentPort`.
- ИИ в поддержке/рекомендациях/watchdog — в v3; звонки и ИИ-менеджер продаж — v4.
- Инфра: одна ВМ, те же 80/443 и IP; диск до этапа 1; 4 vCPU / 8 ГБ перед живым ботом и GPT.
- Live Bitrix24 / 1С по-прежнему нет.
